# 修复反向拖拽判断逻辑

## 问题描述

**现象**：
- 拖拽已勾选的章节时，期望取消勾选
- 实际上章节仍然保持勾选状态
- 反向拖拽功能未生效

**原因**：
判断条件使用了 `>=`（大于等于），导致在已勾选和未勾选数量相等时，也会进入反向取消逻辑，但这可能不是用户的真实意图。

---

## 修复方案

### 修改判断条件

**之前的逻辑**：
```python
if selected_and_checked and len(selected_and_checked) >= len(selected_and_unchecked):
    # 反向拖拽：取消勾选
```

**问题**：
- 当已勾选 = 未勾选时（例如各2个），也会判定为反向拖拽
- 这种情况下用户意图不明确，应该默认为正向累加

**修复后的逻辑**：
```python
if selected_and_checked and len(selected_and_checked) > len(selected_and_unchecked):
    # 反向拖拽：取消勾选
else:
    # 正向拖拽：勾选新项目（默认行为）
```

**改进**：
- 使用严格大于 `>`，只有已勾选项明显多于未勾选项时，才判定为反向拖拽
- 相等或未勾选项更多时，默认为正向累加（更符合用户习惯）

---

## 判断规则对比

### 修复前（`>=`）
| 已勾选 | 未勾选 | 判定结果 | 问题 |
|--------|--------|----------|------|
| 3 | 1 | 反向取消 | ✅ 正确 |
| 2 | 2 | 反向取消 | ❌ 意图不明确 |
| 1 | 3 | 正向累加 | ✅ 正确 |

### 修复后（`>`）
| 已勾选 | 未勾选 | 判定结果 | 说明 |
|--------|--------|----------|------|
| 3 | 1 | 反向取消 | ✅ 明显是取消意图 |
| 2 | 2 | 正向累加 | ✅ 默认累加更安全 |
| 1 | 3 | 正向累加 | ✅ 明显是累加意图 |

## 使用示例

### 场景1：明确的反向拖拽
```
已选中：1,2,3,4,5
拖拽：第2-4话（3个已勾选，0个未勾选）
→ 3 > 0，判定为反向拖拽
→ 取消勾选 2,3,4
结果：已选中 1,5
```

### 场景2：混合拖拽（相等）
```
已选中：1,2,3
拖拽：第2-5话（2个已勾选，2个未勾选）
→ 2 = 2，不满足 > 条件
→ 判定为正向拖拽（默认行为）
→ 勾选 4,5
结果：已选中 1,2,3,4,5
```

### 场景3：明确的正向拖拽
```
已选中：1,2,3
拖拽：第5-8话（0个已勾选，4个未勾选）
→ 0 < 4，不满足 > 条件
→ 判定为正向拖拽
→ 勾选 5,6,7,8
结果：已选中 1,2,3,5,6,7,8
```

---

## 设计原则

### 1. 安全优先
- 相等情况下，默认为正向累加
- 避免误删用户的选择

### 2. 意图明确
- 只有在明显是反向拖拽时才取消
- 已勾选项必须明显多于未勾选项

### 3. 用户友好
- 正向累加是更常见的操作
- 默认行为应该是累加而不是取消
