# 故障排查

先保留失败现场：不要立即删除 `models/`、`config/` 或 `manga_translator_work/`。桌面端每次启动会在 `result/` 创建 `log_YYYYMMDDHHMMSS.txt`，文件日志始终记录 DEBUG 级别；未捕获的 Python 异常和部分原生崩溃信息也写入同一文件。

## 最小诊断信息

报告问题时建议提供：

- 操作系统、CPU/GPU 型号与安装的依赖方案（CPU/NVIDIA/AMD/Metal）。
- 使用的工作流和所选检测、OCR、修复、翻译、渲染模型。
- 可复现的最小图片或脱敏 JSON。
- 最新 `result/log_*.txt` 中从任务开始到错误堆栈的片段。
- 是否能在 `cli.batch_size=1`、关闭 `cli.batch_concurrent` 后复现。

分享日志和配置前删除 API Key、私有 Base URL、用户名、文件路径和原图内容。

## 启动或导入失败

### Python 版本不匹配

源码环境只支持 Python `>=3.12,<3.13`。优先运行项目的安装/更新脚本，让 `uv` 管理 `.venv`；不要在系统 Python 3.11 或 3.13 中混装依赖。

```powershell
uv python install 3.12
uv sync --no-default-groups --group cpu
uv run --no-sync python desktop_qt_ui/main.py
```

NVIDIA 环境使用 `gpu` 组，Linux AMD 使用 `amd`，Apple Silicon 使用 `metal`。Windows AMD 应走维护安装器，因为它会处理 Radeon SDK 与 PyTorch 的安装顺序。

### Qt、Torch 或 ONNX DLL 错误

确认启动脚本使用的是项目 `.venv` 或便携包自带 Python，而不是 PATH 中另一套解释器。不要把 CPU、GPU、AMD、Metal 依赖组同时装进一个环境；`pyproject.toml` 明确把它们声明为互斥组。

若只有 ONNX Runtime GPU 初始化失败，可在设置中启用 `cli.disable_onnx_gpu`，或命令行/Web 设置 `MT_DISABLE_ONNX_GPU=true`。这会让 ONNX 走 CPU，但 PyTorch 模型仍可使用 GPU。

## GPU 没有启用

`cli.use_gpu=true` 只是请求使用 GPU，不能把 CPU 版 PyTorch 变成 GPU 版。检查：

```powershell
uv run --no-sync python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'no CUDA')"
```

当前 NVIDIA 依赖组绑定 PyTorch CUDA 13.0 索引，驱动必须支持对应运行时。macOS Metal 通过 MPS，不会让 `torch.cuda.is_available()` 返回 true。Windows AMD 也不要用 CUDA 作为判断标准。

## 显存或内存不足

典型日志包含 `CUDA out of memory`、ONNX 分配失败或进程被系统终止。按影响从小到大尝试：

1. 把 `cli.batch_size` 调为 `1`，关闭 `cli.batch_concurrent`。
2. 降低 `detector.detection_size` 和 `inpainter.inpainting_size`。
3. Real-CUGAN 设置较小的 `upscale.tile_size`，或关闭翻译前超分。
4. 启用 `app.unload_models_after_translation`。
5. ONNX 特有问题启用 `cli.disable_onnx_gpu`；修复器特有问题可尝试 `inpainter.force_use_torch_inpainting`。
6. 改用 CPU 依赖方案或更轻的模型。

`PYTORCH_ALLOC_CONF=expandable_segments:True` 已由入口默认设置，重复设置通常不能解决模型本身超过显存容量的问题。

## 模型下载失败

离线模型位于 `models/<组件>/`，多数模型提供多个下载来源。检查网络、代理、磁盘空间和目录写权限。下载中断后从日志找到具体文件，只将该文件或对应组件目录移到别处，再重启触发下载。

不要随意从第三方下载同名权重覆盖；模型结构匹配但权重版本不匹配也可能到推理阶段才报错。容器部署还要持久化 `/app/models`，否则重建容器会重复下载。

## API 调用失败

| 症状 | 优先检查 |
| --- | --- |
| 未配置/401 | 当前后端对应的 `.env` Key；专用 OCR/上色/渲染组是否应回退到通用组 |
| 404/模型不存在 | `API_BASE` 是否包含正确版本路径（OpenAI 兼容服务常为 `/v1`）；模型名是否由该端点提供 |
| 429 | 服务配额、`max_requests_per_minute`、轮换槽位和冷却状态 |
| 400 参数错误 | 暂时关闭 `use_custom_api_params`；确认所选模型支持图片输入或图片生成 |
| 返回数量不一致 | 恢复 HQ 输出格式提示；减少上下文/批量；检查服务是否截断响应 |
| 本地兼容端点要求 Key | 即使服务不校验，也可在 `.env` 填任意非空占位值 |

修改 `.env` 后重启应用可排除旧客户端缓存。轮换配置中 Key、Base、Model 必须使用相同编号组成一个端点。

## 检测不到文字或误检太多

- 先确认输入图片能被 Pillow 正常打开，且不是全透明或损坏文件。
- 漏检时适当降低 `detector.text_threshold`、`box_threshold`，或提高 `detection_size`。
- 误检时提高阈值，检查 `use_sfx_filter`、`use_model_bubble_filter` 和 `ignore_bubble` 是否符合页面类型。
- `filter_text_enabled` 可能让 OCR 结果被 `filter_list.json` 删除。
- `translator.keep_lang` 会在文本合并后排除其他来源语言；不需要时设为 `none`。
- 导入 YOLO 标签时，文件必须位于 `manga_translator_work/yolo_labels/<图片基名>.txt`，旧版图片同目录标签也可兼容。

先运行“导出原文”工作流观察检测/OCR 结果，可以把问题与翻译、修复、排字阶段隔离。

## 原文没有擦干净

逐步增加 `mask_dilation_offset` 和 `kernel_size`，不要一次调得过大，否则会侵蚀气泡边框或人物线稿。气泡模型相关选项会限制/修复蒙版交集；对音效字和无气泡文字可能反而裁掉需要修复的区域。

可以先运行“仅修复”检查 `manga_translator_work/inpainted/`，再在编辑器使用蒙版画笔/橡皮修正。复杂背景可尝试 `lama_large`、`lama_mpe` 或分块修复。

## 排字异常

- 方向错误：把 `render.direction` 从 `auto` 临时改为 `horizontal` 或 `vertical`。
- 文字溢出：使用 `smart_scaling`，检查 `max_font_size`、`font_scale_ratio`、固定 `font_size` 和手工文本框尺寸。
- 必须限制在框内：使用 `strict` 或启用严格布局。
- 气泡英文排版：尝试 `balloon_fill` 或 `bubble_layout_english`。
- 断行不稳定：检查译文中的 `[BR]`、`semantic_linebreak`、`optimize_line_breaks` 和 `check_br_and_retry`。
- 符号旋转/替换错误：检查 `text_replacements.yaml` 与 `rich_text_rules.yaml` 的方向组和规则顺序。

## JSON 或文本导入没有生效

确认文件基名和目录：

```text
manga_translator_work/json/page001_translations.json
manga_translator_work/originals/page001_original.<模板扩展名>
manga_translator_work/translations/page001_translated.<模板扩展名>
```

程序仍兼容图片旁的 `page001_translations.json`，但新目录优先。`translation_template.json` 的 `output_format` 改变后，旧的 `.txt`/`.json` 文本导出不会自动改名。原文导出、译文导出和 JSON 内容冲突时，加载流程可能优先采用文本导出。

批量管理默认在 JSON 旁写 `.bak`，可从批量页恢复一次。若编辑器与批量任务同时保存，最后一次写入会胜出；先关闭其中一个写入者再恢复备份。

## 压缩包无法打开

- PDF 依赖 PyMuPDF；标准依赖中包名是 `PyMuPDF`，导入名是 `fitz`。
- CBR 除 Python 的 `rarfile` 外，还需要系统可用的 RAR 解压后端。
- EPUB/CBZ/ZIP 必须是有效 ZIP 结构，且内部图片扩展名在支持表中。
- 同名解压目录可能因 `.archive_source.txt` 指向另一归档而触发冲突提示。

先把归档手工解压成图片目录可判断问题在归档层还是翻译层。

## 配置损坏或升级后字段异常

1. 退出应用并备份 `.env`、`config/`、`dict/` 和 `presets/`。
2. 用 JSON/YAML 校验器检查手工编辑的文件。
3. 若仅 `config/config.json` 损坏，可将它改名后启动；程序会从 `config-example.json` 重建。
4. 文本替换、富文本规则和提示词可在相应桌面编辑器中重置为内置模板。
5. 不要删除 `config-example.json`，配置同步依赖它。

## Web 首次设置、401 与权限错误

先检查认证状态：

```bash
curl http://127.0.0.1:8000/auth/status
```

- `need_setup: true`：访问 `/static/login.html` 或调用 `/auth/setup` 创建第一个管理员。
- 翻译返回 `NO_TOKEN`：在请求头加入 `X-Session-Token`。
- 返回 `INVALID_TOKEN`：会话无效或已过期，重新登录；当前会话超时为 60 分钟。
- 返回 `403`：检查用户和用户组允许的翻译器、OCR、上色器、渲染器、参数和工作流。
- 返回配额或并发限制：在管理端检查该用户/用户组限制与当前任务。

`MANGA_TRANSLATOR_ADMIN_PASSWORD` 只写入旧的服务管理密码设置，不会创建登录账号，不能用它直接登录 `/auth/login`。

## Web 端口冲突或无法访问

先只监听本机测试：

```bash
uv run --no-sync python -m manga_translator web --host 127.0.0.1 --port 8000 -v
```

Windows 查看占用：

```powershell
Get-NetTCPConnection -LocalPort 8000 -ErrorAction SilentlyContinue
```

Linux 查看占用：

```bash
ss -ltnp | grep ':8000'
```

如果本机可访问、其他主机不可访问，再改为监听 `0.0.0.0`，并检查系统防火墙、云安全组和反向代理。浏览器地址不能写 `0.0.0.0`，应使用服务器的实际 IP 或域名。

## Docker 问题

CPU 服务诊断：

```bash
cd packaging
docker compose ps
docker compose logs --tail=300 manga-translator-cpu
```

GPU 服务诊断：

```bash
cd packaging
docker compose ps
docker compose logs --tail=300 manga-translator-gpu
```

常见原因：

- CPU 服务映射宿主机端口 `8000`，GPU 服务映射 `8001`。
- GPU 容器缺少 NVIDIA Container Toolkit，或宿主驱动无法向容器提供 GPU。
- `data/config`、`data/fonts`、`data/dict` 或 `data/server` 对容器不可写。
- 没有持久化 `data/models`，导致容器重建后重新下载模型。
- Compose 中 `.env` 挂载默认被注释，管理端保存的服务器密钥不会随容器重建保留。
- 健康检查有 60 秒启动等待；首次初始化更久时，应结合容器日志判断，不要只看短暂的 `unhealthy`。

完整服务、端口和挂载说明见 [[Web 服务与 Docker|12-Web服务与Docker]]。
